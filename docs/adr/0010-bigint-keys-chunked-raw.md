# ADR-010 : Clés `bigint` identity et brut en base par morceaux

- **Statut :** accepté
- **Date :** 2026-11-07
- **Références :** `docs/ARCHITECTURE.md` §2, §4.1, §4.2, §4.4 et §5.1

## Contexte

- Le modèle EF Core est unique pour PostgreSQL et SQL Server.
- Les clés `Guid` (même v7) fragmentent les index cluster sous SQL Server ; les clés séquentielles ne le font sur aucun des deux fournisseurs.
- Les rapports bruts envoyés par l'uploader (jusqu'à 200 Mo par requête, davantage une fois décompressés) doivent être conservés pour le retraitement, puis purgés après la durée de rétention.
- Le déploiement ne comporte aucun stockage objet (ni MinIO ni blob storage) : toute la donnée vit dans la base.

## Décision

- **Clés primaires `bigint` identity** (`GENERATED BY DEFAULT AS IDENTITY` sous PostgreSQL, `IDENTITY(1,1)` sous SQL Server).
- Les identifiants exposés publiquement ne sont pas les clés internes : `Uploads.PublicId` (`uuid`) et les identités naturelles (`owner/name`, SHA, numéro de PR).
- **Le brut est stocké en base, par morceaux** (`byte[]`, `bytea` / `varbinary(max)`), écrit en flux pendant la réception de l'upload, sans charger le corps entier en mémoire.
- Le brut est purgé par lots par le job `PurgeExpiredData` (`Retention:RawDays`, 30 jours par défaut).

## Conséquences

- **Positives :**
  - index compacts et insertions séquentielles sur les deux fournisseurs ;
  - sauvegarde et restauration d'un seul composant (la base) ;
  - réception en flux, mémoire bornée quelle que soit la taille de l'upload.
- **Négatives :**
  - la base porte le volume des rapports bruts pendant la rétention, d'où la purge par lots et la décision encore ouverte sur la durée de rétention ;
  - les clés internes ne doivent jamais apparaître dans une URL publique : les contrats exposent les identifiants publics.
